<objective>
Implement ADR-0006 in the loader, the validator and the number authority: an empty `tacticity` is
resolved to the label of its twin before the candidate identity is taken, when the same
`canonical_psmiles` carries exactly one non-empty label elsewhere in the snapshot.

Purpose: 301 materials are currently split into two candidates each, so their replicates are never
pooled, their replicate noise floor is not measured, and one beam could present the same repeat unit
twice. D-25 decided the rule; ADR-0006 is the instrument that changes the candidate definition frozen
at M1 (charter §7, CHANGE-POLICY § Interface freezing). This plan is that change.

Output: the rule, its two guards, the republished `docs/audit/polyomics-041e5834-validation.md`, and
every Phase-2 and Phase-3 expectation that quoted a pre-ADR candidate-level number brought green in
the same commit.

Numbers this plan states as targets, from ADR-0006 and the owner's 2026-09-24 measurement on the
pinned snapshot (the plan is their only source; the executor reproduces them, it does not re-derive
them differently):

- source rows 95,335; in-scope rows 95,332 — both unchanged
- 554 in-scope rows with an empty `tacticity` -> 312 `none`, 182 `atactic`, 0 `isotactic`,
  0 `syndiotactic`, 60 left `"unknown"`
- exactly 2 canonical SMILES carry more than one distinct label and keep `"unknown"`
- candidates 78,676 -> **78,375** (-301)

Of that last line, **78,375 is the measured value and -301 is its arithmetic consequence**, not a
second, independent derivation. The two are one fact, so they cannot cross-check each other: if the
loader prints any other candidate count, nothing in this plan corroborates 78,375 and the only
correct response is Task 2b STEP 4's halt — the rule and ADR-0006 disagree and the owner decides
which is wrong. Do not reconcile a mismatch by subtracting 301 from whatever the loader printed.

Every other candidate-level number — the candidate-level triple in both orders, the replicate
structure, the per-property noise floor, the feasible set, the ε_dc candidate Q25, the canonical
tacticity-twin counts — moves by an amount this plan deliberately does not state. The validator
republishes each one and the executor records the delta (CHANGE-POLICY § Numbers: a number is
published in one place; the validator is that place).

Where the commit boundaries fall, and why. R-4 requires the seven-step gate to pass before every
commit, so the boundaries are decided by which commits can be green, not by which are convenient.
Two green seams exist ahead of the flip and this plan uses both:

- **Task 2a** adds `observed_labels`, `resolve_tacticity` and `tacticity_resolution_counts` with no
  call site, plus `row_index` in the validator's column selection. Nothing calls the rule, no
  finding moves and no report byte changes, so the gate is green and the commit stands on its own.
  It also gives Task 2b a fixed **pre-flip sha** to diff the row-level expectations against — the
  seam is not only a context saving, it is what makes the row-level guard a command.
- **Task 2b** flips one line in `load.add_identity`. From that line onward every consumer of the
  candidate table — the synthetic fixture, the Phase-2 validator expectations, the real-file
  reproductions, the Phase-3 evaluator tests and the committed protocol example — is red at once.
  That step genuinely is irreducible: there is no ordering of those edits in which an intermediate
  commit is green, because they all read the same table.

So the change is not one indivisible lump, as an earlier draft of this plan claimed; it is a green
preparatory commit followed by one irreducible flip. Task 2b remains the dominant cost, and the plan
carries the full file inventory and the named assertion sites so the executor spends its context
editing rather than rediscovering.
</objective>
