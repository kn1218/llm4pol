## 1. Claims and results

### 1.1 Abstract-level claims (`Manuscript.txt:2`, lines 15-29)

1. A closed-loop multi-agent framework converts a natural-language target into "chemical hypotheses, constraints, diagnostic tests, and feedback"; Agent 1 proposes hypotheses over metal nodes, linkers, pore geometry, functionality; Agent 2 converts them to constraints selecting MOFs defined by (node, linker, topology).
2. The Matchmaker forms **four beams** "to attribute gains to geometry, chemistry, or metal choice: full hypothesis, chemistry, metal only, and random baseline."
3. "Blind to database landscapes, LLM4MOF enriches top performers across six adsorption, separation, and electronic-structure tasks within 400 evaluations."
4. It "designs and live-simulates de novo MOFs spanning H2 storage, SF6 capture, and C2H6/C2H4 separation, deriving a distinct design rule for each objective."
5. "Under an identical nominal evaluation budget it consistently outperforms random search, Bayesian optimization, and genetic algorithms, and the outcome is insensitive to the language-model backend."
6. "All of this uses not a single property-labeled training structure."
7. Discussion (`Manuscript.txt:22`, l. 618-622): "The central contribution is not that a language model can drive MOF search, but that it can do so attributably."

## 2. The closed loop, step by step

### 2.1 Iteration count and stopping rule
Fixed **ten iterations, no early stopping** (SI Note S1 `SI.txt:4`, l. 62-66). An iteration whose constraints match no candidate "produces no structures and consumes no simulations; it is retried, and the plotted iteration index counts the iterations that produced candidates." Code: DB mode simply runs `--iterations N` (`run_experiment.py:590-593`, zero-result iterations still count and are auto-continued, l. 512-537); live mode counts `real_iterations` only when RASPA ran, with a safety cap of 3x (`run_live_experiment.py:1539-1557`); matchmaker failure and geometry abort loop back to Agent 1 without incrementing (l. 1679-1712, 1746-1770). `source_data` therefore carries both `iteration` (productive) and `iteration_raw` (on disk) for the discovery CSVs (`source_data/README.md`).

Per-iteration deterministic sequence (`SI.txt:4` l. 70-73): Agent 1 -> Agent 2 -> Matchmaker -> diagnostic sampling -> Hypothesis Testing -> Feedback Generator. Malformed JSON "trigger[s] an immediate iteration halt" (l. 79-80); in code Agent 1/2 returning `None` breaks the loop (`run_experiment.py:431-446`), after `LLMClient.extract_json` has tried four repair strategies incl. closing truncated braces (`core/llm_client.py:325-395`).

### 2.2 Agent 1 — hypothesis generator
- Role: "Hypothesis Generator and Experiment Planner for reticular MOF design" (`prompts/agent1_v3.0_production.md:3`). Multi-turn: keeps its full conversation history across all ten iterations (`SI.txt:4` l. 74-75; `core/agent1_handler.py:40`, `LLMClient(multi_turn=True)`). Temperature 0.0 (`config.py:421`). Backend GPT-5.2 for all reported campaigns (`Manuscript.txt:24` l. 654).
- Inputs: iteration 1 = the user inquiry verbatim, "unenriched" (`SI.txt:4` l. 68-70; `agent1_handler.py:57`); iteration i>1 = a wrapper message + the feedback string (`agent1_handler.py:92-108`, which tells it "The feedback contains 4 diagnostic beams... Compare adjacent beams... State whether you are executing an 'Exploitation Phase' or an 'Exploration Phase'").
- Prompt rules that shape behaviour (`agent1_v3.0_production.md`): "Stateless Execution" (list all metals every time, l. 8); "STAGNATION TRAP" -> Exploration Phase: keep best metals, add >=3 untried metals and >=2 new linker branches (l. 10); a fixed **design toolbox** of descriptors `df, di, vf, sa, density, dif, cv`, `oxidation_states`, `coordination_geometry`, `has_open_metal_sites`, `node_metal`, `node_connectivity`, `linker_length`, `functional_groups`, `min_group_counts`, `building_block_properties` (l. 13-43); "CRITICAL RULE: Do NOT select a specific Topology Code" and "ONLY ditopic (2-connected) linkers" (l. 45-47); Step 3.5 COMMIT-to-REDUCE with an axis menu (pore geometry / functional-group decoration / electronic structure) and "READ-THE-EVIDENCE PROCEDURE" comparing top vs low samples (l. 73-91); FIRST-ITERATION RULE: no numeric geometry bounds in iteration 1 (l. 92); EVIDENCE-BASED EXPLORATION RULE: pivot only toward chemistry seen above current best in Beam 3/4 (l. 94-97).
- **Output JSON schema it must emit** (verbatim, `agent1_v3.0_production.md:111-124`):

```json
{
  "meta_cognition": {
      "reasoning": "Rich text: Why did you choose this hypothesis structure? Describe your reasoning. State whether you are in an 'Exploitation Phase' (refining a rising peak) or an 'Exploration Phase'"
  },
  "target_application": "[Restate User Goal]",
  "hypothesis_mechanism": "[Rich Text: Start with the PERFORMANCE goal. Explain how that dictates the target GEOMETRY and COMPONENTS.(how it does not dictate the geometry or components)]",
  "ideal_pore_geometry": "[Rich text: ONLY if pore geometry is your controlling axis ... when you give target ranges (Di, Df, SA, VF, Density, Dif, CV), make the BOUND DIRECTION match your evidence ...]",
  "node_composition": "[Rich text: Describe the Node chemistry. ... state a COMMITTED connectivity INTEGER ... For electronic metrics, commit metal identity / oxidation state / spin instead.]",
  "linker_composition": "[Rich text: Organic Backbone + Functional Groups + Length + Ligand. ...]",
  "novelty_justification": "[Rich text: Why this specific combination is a valid hypothesis for this application.]",
  "lesson_learnt": "[Rich text: What did you learn from the feedback of the previous iteration? How will you apply it to this iteration?]"
}
```
  Only `target_application, hypothesis_mechanism, node_composition, linker_composition` are checked (`agent1_handler.py:132-134`). The prompt mentions a `database_constraints` block "must include only the supported fields defined in the schema" (l. 107) but the schema shown has none; in practice GPT-5.2 emits an extra `database_constraints` object (`target, df/di/vf/density/sa {min,max}, node_metal[], linker_length, functional_groups[], min_group_counts, building_block_properties`) — see the verbatim example `SI.txt:20-21` l. 783-819 and the recorded `agent1_output.json` in the battery. **Nothing downstream reads `database_constraints`**; Agent 2 reads the prose fields.
- Two prompt builds exist: `agent1_system_prompt_database_campaigns.md` (Figs 2-3, 13,840 chars) and `agent1_system_prompt_discovery_benchmark.md` (discovery + backend benchmark, 16,055 chars, identical to `agent1_v3.0_production.md`); they differ in three auxiliary fields — `min_group_counts` in the toolbox, the READ-THE-EVIDENCE procedure, and the "commit SOFTLY (presence or <=2)" decoration rule replacing "commit specific group COUNTS" (`prompts/README.md`; diff run in Appendix A). SI Note S9 says re-running all DB tasks under the newer build "leaves every conclusion of Figure 2 unchanged" (`SI.txt:20` l. 702-705).

### 2.3 Agent 2 — constraint translator
- Role: "Data Bridge... convert a Chemist's qualitative design hypothesis into strict Quantitative Search Specifications" (`prompts/agent2_v4.1.md`; SI Note S10 `SI.txt:22`). **Stateless** (`LLMClient(multi_turn=False)`, `agent2_handler.py:91`), temperature 0.0 (`config.py:422`), input = `json.dumps(hypothesis)` (l. 115). "You do NOT select a Topology. You do NOT output specific material names."
- Mode-specific rule block `{DATABASE_MODE_RULES}` injected at init (`agent2_handler.py:23-63`): PORMAKE mode -> coordination tags (Carboxyl, Carbonyl, Phosphonate, Sulfonate) must NOT go into linker branches but into `node_query.ligand_chemistry` ("BINDING TERM HANDOVER"); hMOF/QMOF mode -> coordination tags are valid record tags.
- Key translation rules (`SI.txt:22-27`): metals as a list; nuclearity only if it applies to all node families, else null; length in Å, null if unspecified ("do not guess"); `is_rigid` true on "rigid/stiff/alkyne/aromatic backbone"; `functional_groups` = universal AND floor, usually `[]`; alternatives -> `linker_branches` (OR of ANDs), never the common denominator; "OPTIONAL != EXCLUDE"; at most ONE `linker_query.abstract_features` (AND-trap); `preferred_features` = soft ranking bonus only; `backbone_requirements` / `substituent_requirements` / `min_group_counts` only when Agent 1 is explicit; PORMAKE single-building-block rule (composite linker concepts split into one-tag branches); geometry = "PREDICTIONS ... second-stage evaluation gate", all null unless Agent 1 gave numbers; QMOF-only `oxidation_state {Metal: int}`, `geometry_preference` in {Octahedral, Tetrahedral, Square Planar, Linear}.
- **Output schema** (verbatim, `SI.txt:28-29` l. 1221-1273 = `prompts/agent2_v4.1.md`):

```json
{
  "node_query": {
      "reasoning": "...", "metals_include": ["List","Symbols"], "connectivity": [Integer_List_or_Null],
      "nuclearity": Integer_or_Null, "ligand_chemistry": ["Element name of the Ligand atom"],
      "abstract_features": {}, "preferred_features": {},
      "oxidation_state": {"Metal": Int_or_Null}, "geometry_preference": "String_or_Null"
  },
  "linker_query": {
      "reasoning": "...", "connectivity": Integer_or_Null, "length_min": Float_or_Null, "length_max": Float_or_Null,
      "is_rigid": Boolean_or_Null, "functional_groups": ["Universal_Minimum_Tags_or_Empty"],
      "abstract_features": {}, "preferred_features": {},
      "backbone_requirements": [...], "substituent_requirements": [...], "min_group_counts": {"tag": Int},
      "linker_branches": [ {"description": "Branch_Name", "required_tags": ["Tag1","Tag2"]} ]
  },
  "global_requirements": { "include_tags": [...], "exclude_tags": [...], "optional_tags": [...] },
  "geometry_filter": {
      "target_Di_min/max", "target_Df_min/max", "target_sa_min/max", "target_vf_min/max",
```

  Validation is soft: only `node_query, linker_query, geometry_filter` and `metals_include` are required; everything else warns and passes through (`agent2_handler.py:139-213`). Post-extraction, tags present in both include and exclude, or in `linker_query.functional_groups` and exclude, are removed from `exclude_tags` (`run_experiment.py:450-471`).

### 2.4 Controlled chemical vocabulary and how hypotheses become constraints
- Table S4 (`SI.txt:47`): **124 canonical tags** in 10 categories — Backbone 5, Scaffold 16 (Adamantane ... Triptycene), Heterocycle 35, Functional group 39, Substituent 4 (Ethyl, Isopropyl, Methyl, tert-Butyl), Halogen 6, Node-binding element 6 (Boron, Carbon, Nitrogen, Oxygen, Phosphorus, Sulfur), Linker type 6 (Alkene, Alkyl, Alkyne, Butadiene, Butadiyne, Hexatriyne), Metal 3, Topology 4. "Agent 2 emits only these tags, with any variant resolved to its canonical form through a 215-entry alias map." Runtime file `data/unified_vocabulary.json` (27 KB); loaded once by `constraint_utils._load_vocabulary()` -> `canon()` lowercases, replaces `-`/space by `_`, resolves aliases (`constraint_utils.py:98-122`); OLD clone reports 124 canonical / 183 aliases at load.
- Tags come from a **two-layer metadata pipeline** (SI Note S4 `SI.txt:9-10`; `database_construction/SI_METHODOLOGY.md`): Layer 1 deterministic facts (formula, MW, metals, nuclearity, connection points, plane-of-best-fit geometry, edge length, ring sizes, rigidity by bridge analysis, canonical SMILES via RDKit with dummy atoms as Lr); Layer 2 = **105 curated SMARTS** matched bond-order-agnostically (PORMAKE encodes carboxylates as aromatic bonds; fix raised carboxylate detection from 2 to 202 BBs), metal-stripping fallback, multiplicity counts (`rule_based_counts`), generic-tag propagation (`TAG_HIERARCHY` ~152 entries, e.g. `benzene_ring -> aromatic, aryl, ring`), backbone/substituent split hard-coded by pattern category (13 substituent patterns), plus an LLM enrichment step (gpt-4o-mini T=0.3 for QMOF/hMOF, Gemini 2.0 Flash for PORMAKE) that writes only human-facing `readable_name`, `design_hints`, `abstract_features`, `llm_additions` — "This enrichment step writes no fields that the Matchmaker filters against" (`SI.txt:9` l. 245-248; `SI_METHODOLOGY.md` §6.3).
- Constraint semantics enforced identically in all three matchmakers (`constraint_utils.py:171-269, 276-366, 373-403, 478-609`): `global_requirements.include_tags` = AND over (node features U edge features); `linker_query.functional_groups` = OR; `exclude_tags` = bouncer on features **and** on `readable_name` substring (`check_negative_tags`, l. 373-403 — note the name check is an LLM-written field); `linker_branches` = OR-of-ANDs on `functional_groups`; `backbone/substituent/min_group_counts` on `functional_groups_categorized`; unrecognised positive tags are warned but still applied (they simply match nothing), unrecognised negative tags are dropped.

### 2.5 The Matchmaker (SI Note S2 `SI.txt:5-6`; Table S3 `SI.txt:46`)
- **Design space (discovery)**: single-node, single-edge frameworks from **518 metal nodes x 156 two-connected linkers x 952 connectivity-compatible single-node topologies = 12,499,656** (Table S5 `SI.txt:48`: by node connectivity c=3: 58 topos x 28 nodes; c=4: 184 x 122; c=5: 227 x 15; c=6: 223 x 196; c=7: 134 x 5; c=8: 72 x 109; c=9: 31 x 3; c=10: 18 x 10; c=12: 5 x 30). The whitelist is literally the MOF2Zeo vocabulary files `core/mof2zeo/data/{topology,node,edge}.txt` (952/518/156 lines) — `config.py:96-104` calls it the "SINGLE source of truth"; `scripts/build_canonical_db.py` pre-filters the six PORMAKE H2 CSVs to it, and `matchmaker.py:29-33,247-249,334-336` refuses to propose anything outside it. Multi-node/multi-edge/multivariate frameworks are out of scope (`SI.txt:5` l. 108-110).
- **PORMAKE route** (`core/matchmaker.py:378-539`): Phase A topologies = those whose `node_connectivities` set is a single value in the requested connectivities (default `[3,4,6,8,12]` if Agent 2 gave null, l. 394-402) and whose edge connectivity == 2 (l. 80-147); Phase B nodes per connectivity: metals OR-match (`"Any"` wildcard), nuclearity exact, `ligand_chemistry` intersection, negative bouncer, node `abstract_features` AND (unknown = benefit of doubt) (l. 212-294); Phase C linkers: connectivity, length in [min,max] (defaults 0..999), `is_rigid`, bouncer, linker `abstract_features` **OR** (l. 185-210, the "AND-trap" fix), branch matching after coordination tags are stripped (l. 321-323); Phase D "virtual assembly": keep only nodes/edges that form at least one (node, edge) pair satisfying the AND/OR union logic (l. 464-504); Phase E categorized-group filter (l. 507-526). Returns `{"topology": [...], "topology_by_cn": {cn: [...]}, "node": [...], "edge": [...], "diagnostics": {total_linkers, cn_match, len_match, rigid_match, chem_match, af_match, final_match}, "preferred_features": {...}}` or a structured error `{"status":"error","reason":"no_matching_nodes",...}` (l. 443-453).
- **hMOF / QMOF route** = whole-record filtering (`core/hmof_matchmaker.py:128-238`, `core/qmof_matchmaker.py:129-207`): negative tags, metals, topology (optional), open-metal-site flag, AND tags, OR tags, branches, categorized groups; hMOF adds optional structural range filters; QMOF adds connectivity, oxidation state (per entry metal), coordination geometry. `search_mode` in {full, metal_only, linker_only} is how the beams are built (§2.6). Output = list of ids.
- **Metadata each DB provides** (Table S3 `SI.txt:46`; `data/DATABASE_CONDITIONS.md`): PORMAKE BBs: metals, connectivity/nuclearity, SBU type/coordination geometry, ligand/donor chemistry, SMARTS tags + counts, backbone/substituent split, edge length, rigidity, ring sizes; pore geometry only after assembly (Zeo++ or MOF2Zeo). hMOF (51,163 records; metals only Zn 62%/Cu 26%/V 7%/Zr 5%; `metal_node` fields all None, `SI_METHODOLOGY.md` §7.1): metal list, MOFid topology (75% pcu), SMARTS tags, tabulated `lcd, pld, surface_area_m2g (actually m2/cm3, key name legacy — config.py:361), void_fraction, density` and GCMC uptakes `ch4_uptake_35bar_298K (cm3STP/cm3), co2_uptake_2_5bar_298K (mol/kg), h2_uptake_{2,100}bar_77K (g/L), xe/kr_loading_1bar_273K (mol/kg), xekr_selectivity_1bar`. QMOF (20,373 DFT records of synthesised MOFs; 16,894 linker SMILES parsed; topology for 65%): metals, nuclearity, oxidation states, spin, coordination geometry, `connectivity_points`, SMARTS tags, `info.lcd, info.pld, info.density, info.volume`, `outputs.pbe.bandgap` (+ HLE17/HSE06). Column mapping to the analyzer's `di, df, sa, vf, density, dif, cv` is in `config.py:358-365` and `sensitivity_analyzer.py:47-114` (hMOF `dif := df`, `cv := 0`; QMOF `sa := 0, vf := 0`).
- **Naming for the LLM**: BB ids (`N164`, `E70`) are translated to `readable_name` via `core/name_resolver.py` ("Node: zirconium octahedral node | Linker: butadiyne-bridged benzene linker"); hMOF/QMOF rows are described as `metals topology | Bkbn:[...] Subs:[...]` (`feedback_generator.py:124-191`). Structures get anonymous labels `MOF-{idx}` in the chemistry profile (l. 218-220) — but the readable names are shown.

### 2.6 The four diagnostic beams (SI Note S3 `SI.txt:7-8`; Methods `Manuscript.txt:25`)
Definitions (exact, from code):

| Beam | Paper | DB mode: `sensitivity_analyzer.run_analysis` | Live mode: `live_runner._build_beam_specs` |
|---|---|---|---|
| 1 / `Z` full | full hypothesis: chemistry + geometry window as strict second-stage gate | `set_z` = rows whose (node, edge) are in the matchmaker's lists AND pass union logic (= `set_a`) AND `DI_MIN < di < DI_MAX`, `DF_MIN < df < DF_MAX` (strict) AND `sa, vf, density, dif, cv` within [min,max] (inclusive) (`sensitivity_analyzer.py:660-701`); hMOF/QMOF: `set_a` = matched ids then same numeric gate (QMOF falls back to `set_z = set_d` when sa/vf absent, l. 716-719) | full specs; MOF2Zeo-ranked pool of 100, stage-1 build+relax+Zeo++, strict Zeo++ gate, top `LIVE_SIM_Z_RASPA_TOP=10` to RASPA with fallback fill by geometry score (`live_runner.py:1085-1223`) |
| 2 / `A` chem | chemistry only, geometry window removed | `set_a` (chemistry-only) | specs minus `geometry_filter`; random 30, no MOF2Zeo (`_random_ranked_pool`) |
| 3 / `F` metal | metal only; linker and geometry unconstrained | `set_f` = rows whose node id is in `_get_node_list(node_query)` (metals + connectivity + ligand chemistry; no linker constraint) (l. 559-563, 663); hMOF/QMOF: `match(search_mode="metal_only")` | `linker_query` stripped of `functional_groups, linker_branches, abstract_features`; `global_requirements` dropped; **geometry_filter kept** (`live_runner.py:862-870`) — a small live/DB asymmetry (the F beam in live mode still carries the geometry window, though only Z is MOF2Zeo-ranked/gated, so in practice it has no effect) |
| 4 / `total` random | random baseline from the entire database (DB: metal-balanced stratified; live: uniform over generative space) | `df_total` = the whole hidden table (l. 573); sampling is metal round-robin because `STRATIFY_RANDOM_BEAM` defaults True (`config.py:449-455`, README:32-36; commit 5adb33e) | `_build_random_pool`: uniform random (topology in SIM_SAFE, node, edge) with connectivity check (`live_runner.py:875-906`) |

Extra sets exist only for the human sensitivity report (B..S: chem+Di, chem+Df, geometry-only E/E2, linker-only G, single-descriptor H..N, chem+one-descriptor O..S; `sensitivity_analyzer.py:666-748, 874-885`); `e2` (full geometry only) also drives the diagnostic footer ("[GEOMETRY MISMATCH] Your chemistry is valid, but ..."; `feedback_generator.py:569-638`).

Candidates per beam shown to Agent 1: **up to 10** (`FEEDBACK_SAMPLE_SIZE = 10`, `config.py:409`: "10 x 4 beams x 10 iters = 400"). DB mode draws a fresh random sample each iteration (`STOCHASTIC_SAMPLING`, random seed logged per iteration, `feedback_generator.py:48-58, 446-463`) after `sampling_strata.stratified_reduce` (metal round-robin, identity only, target never read; `sampling_strata.py:76-100`); live mode shows `nlargest(n, 'target')` of the successes (l. 449-451). The whole matched set (not the 10) is what `beam_data.csv` records and what the paper's per-iteration "beam median" plots (`run_experiment.py:571-586`; `source_data/README.md` "beam_data.csv (the full scored candidate pool)"). In a recorded campaign the iteration-10 pool sizes were Z 43 / A 257 / F 3,591 / R 9,533 (= whole DB) with medians 563.8 / 515.2 / 506.3 / 501.9 cm3/cm3 (Appendix A).

How beams are compared to attribute causes (`SI.txt:7` l. 173-176; `feedback_generator.py:725-728, 736-749`): Beam 1 vs 2 -> contribution of the geometry window; Beam 2 vs 3 -> linker chemistry; Beam 2 vs 4 -> chemistry vs chance. The attribution is **read by Agent 1 from the text** ("Compare with Beam 2: does your geometry prediction improve or hurt performance?") and by the authors from the replicate-averaged beam medians in Fig. 2/4/5; there is no automated attribution statistic in the loop. The `geometry_null` flag prints "Beam 1 = Beam 2 (no geometry gate was active). This comparison does NOT measure geometry contribution." when `geometry_filter` is all-null (l. 753-760).

### 2.7 Sampling strata
Metal-stratified round-robin (`core/sampling_strata.py`): group candidates by node metal identity (`metal_of(filename)` parses `N*` from `topo+N+E`, or looks up `metals` in the hMOF/QMOF index), shuffle within group, take one per metal in turn until n (`stratified_reduce`, l. 76-100); live variants `stratified_select_dicts` / `stratified_rank_select` preserve rank order within metal (l. 103-160). Config comments call it "The only fully cross-app-validated universal lever" (`config.py:432`) and note that balancing the random beam raises its median from 183.1 to 196.6 on the 77 K/5 bar task (l. 449-455). Metal visiting order is first-appearance unless `SHUFFLE_METAL_ORDER` (default off) — on a target-sorted table this means "the same n metals in every iteration of every run" (l. 457-463). OLD adds `LLM4MOF_STRATA_MODE` = metal | uniform | pore_quartile | topology | edge (aide2 W2 arms V0-V4).

### 2.8 The memory ledger (SI Note S3, S11; Methods `Manuscript.txt:24-25`)
- Formula: feedback F_i = union of beams {full, chem, metal, rand}; ledger pool A_<i = union over j<i of {full, chem, metal} beams only; user message u_i = Wrapper[D(A_<i) || F_i] (`SI.txt:7` l. 185-199). Random beam excluded "so the markscheme CSV oracle is never leaked to Agent 1" (`memory_ledger.py:14-16, 29-33`).
- What D stores (`memory_ledger.py:172-254`, K = `frontier_k` = 10): `global_best {value, iter, beam, hypothesis_id, structure, filename, geometry{di,df,sa,vf,density}}`, `frontier` = top-K distinct structures (dedup by filename), `geometry_envelope` = per-descriptor [min, max, median] over the frontier (descriptors with zero spread dropped, l. 396-416), `history[]` per iteration `{iter, hypothesis_id, parent, best_this_iter, topk_cutoff, topk_median, new_entries, outside_promising, beam_medians{z,a,f,total}, verdict}`. Direction-aware (`LEDGER_DIRECTION` env, `feedback_generator.py:696`). Persisted as `memory_ledger.json` in the experiment dir.
- What Agent 1 sees — production renderer `render_facts_only` (l. 544-584), prepended to the feedback: "=== DESIGN MEMORY (factual record of YOUR best sampled structures so far — no directives) ===", `Best so far`, top-K cutoff and median, top 5 best-first with iteration, geometry ranges (observational), "Best-of-top-K progress (cutoff per iter): i1:... -> i2:...". The legacy `render_for_agent` with exploit directives ("CONCENTRATE... do NOT switch families", "GRAFT it") was found to hurt PORMAKE rare-peak tasks and is not used (l. 548-553).
- Firewall: the ledger ingests only the <=10 sampled rows per beam that the agent saw, not the full `filter_sets` (`feedback_generator.py:679-710`).
- Ablation (Note S11 `SI.txt:31`; Table S6 `SI.txt:49`): 9 tasks x 5 replicates, iteration-10 Beam-1 value without/with ledger: vol H2 5 bar 31.9/33.0 (+1.1), vol 100 bar 51.1/51.1, grav 5 bar 21.5/26.0 (+4.5), grav 100 bar 171.4/213.1 (+41.7), CH4 153.4/159.3 (+5.9), CO2 10.9/12.3 (+1.4), Xe/Kr 16.0/25.3 (+9.3), BG>4 4.0/4.6 (+0.6), BG<0.1 0.6/0.6. "Positive or neutral" on the median metric; on the single-peak metric "net-neutral to slightly negative on the rare-peak PORMAKE applications"; metal-stratified sampling is credited as "the primary mechanism for raising the absolute performance ceiling".

### 2.9 MOF2Zeo (SI Note S5 `SI.txt:11`; Fig. S6)
- What: a MOF-NET-style embedding model (`core/mof2zeo/model.py`, `config.yaml`: 128-d embeddings for topology/node/edge, hidden 64 -> 32, 7 outputs) predicting the seven Zeo++ descriptors `sa, cv, density, vf, di, df, dif` (`feature_name.txt`) from the categorical triple. Trained on 545,107 / validated on 84,228 assembled structures (629,335 descriptor records, `SI.txt:34`), AdamW lr 1e-3, batch 256, cosine warm-up, 500 epochs, seed 1; average R2 0.99 (`SI.txt:11` l. 283-289). Checkpoint `epoch=487-step=1039440.ckpt` (78 MB LFS); training CSVs not shipped (`docs/PROVENANCE.md`).
- Why: geometry "emerges only from the assembled framework"; without a surrogate, satisfying a geometry hypothesis "would otherwise require assembling and relaxing every combination" (`Manuscript.txt:14` l. 447-452). Used **only for triage** of Beam 1: enumerate CN-valid combinations from the matchmaker lists (cap `LIVE_SIM_MAX_COMBOS = 5000`, random subsample), predict, score against the geometry window expanded by the model's per-descriptor MAE (`GEOM_MARGIN_MODE="mae"`: di 0.746 Å, df 0.751, dif 0.828, sa 50.7, vf 0.0098, density 0.0152; `live_runner.py:107-121, 199-238`), rank by weighted in-range score (equal 1/7 weights, linear penalty outside; `filter_candidate.py:412-553`) plus a preferred-features bonus capped at 0.15 (l. 458-498), metal-stratified select the top 100 (`LIVE_SIM_Z_POOL_SIZE`). "surrogate errors can affect which candidates are tried first, but cannot by themselves determine the final accepted geometry" (`SI.txt:11` l. 290-293) — all gating uses recomputed Zeo++ values. OOV topologies fall back to index 0 with a warning (`filter_candidate.py:209-229`).

### 2.10 The oracle: structure optimisation + GCMC (Methods `Manuscript.txt:26`; SI Note S12 `SI.txt:32`; `hpc/run_mof_sim.py`)
- Per structure, on the HPC node (`run_mof_sim.py:155-642`): **PORMAKE** `builder.build_by_type(topology, {0: node}, {(0,0): edge})` -> CIF (rejects multi-node-type topologies and CN mismatch); **LAMMPS** via `lammps_interface` (UFF, harmonic bonds, cutoff 12.8 Å, no h-bonding, `fix_metal=False`) then an appended block: `min_style cg`; loop 2x { `minimize 1.0e-4 1.0e-6 1000 10000`; `fix box/relax aniso 0.0 vmax 0.001`; `minimize ...`; `unfix` }; final `minimize`; `write_data` (l. 273-289; 15-min timeout `LIVE_SIM_LAMMPS_TIMEOUT=900`); ASE converts the data file back to CIF (l. 314-332); **Zeo++** `network -sa 1.2 1.2 5000`, `-vol 1.2 1.2 50000`, `-res` (probe 1.2 Å, no `-ha`) -> `sa (m2/cm3), cv, density, vf, di, df, dif` (l. 357-430); **RASPA3** `simulation.json` built by `build_sim_json` (l. 498-578): `SimulationType MonteCarlo`, `NumberOfCycles 5000`, `NumberOfInitializationCycles 5000` (`config.py:588-589`), `PrintEvery 1000`, `NumberOfUnitCells` = ceil(2 x 12.8 / cell length) per axis, `ExternalTemperature/Pressure` from the adsorbate config, `ChargeMethod` "None" for H2/CH4/XeKr/SF6/C2 and "Ewald" + `UseChargesFrom: CIF_File` for CO2 (DDEC6 charges pre-assigned locally with PACMAN-charge between R1 and R2, `run_live_experiment.py:275-486`), moves Translation 1.0 / Reinsertion 1.0 / Rotation per adsorbate / Swap 2.0 above 30 bar else 1.0 / Widom 1.0. Force fields shipped as RASPA3 JSON: `UFF_H2` (hydrogen united atom with Feynman-Hibbs, `Manuscript.txt:26` l. 729-731), `UFF` (CH4, CO2), `UFF_XeKr`, `TraPPE_C2` (CH3 98.0 K/3.75 Å, sp2 CH2 85.0 K/3.675 Å), `DellisSamios_SF6`; Lorentz-Berthelot, no tail corrections (`SI.txt:32` l. 1428-1432). RASPA timeout 2 h (`config.py:758`).
- Result per structure (`run_mof_sim.py:743-759`): `{filename, topology, node, edge, beam_id, pipeline, predicted_geometry, match_score, status ∈ {success, build_fail, lammps_fail, zeo_fail, stage1_done, stage2_fail, raspa_fail, missing}, cif_path, real_uptake, real_geometry, error_msg, wall_seconds, stages{pormake,lammps,zeo,raspa:{status,seconds,error}}}` written as `results/<filename>.json` plus a `<filename>.DONE` sentinel (l. 933-945). `real_uptake` = `{loading_mol_kg, loading_excess_mol_kg?, henry_mol_kg_pa?, loading_g_L (= mol/kg x density x MW), loading_mg_g?}` for single components or `{component_loadings_mol_kg{a,b}, selectivity, xe_/kr_ legacy aliases}` for mixtures (`raspa_utils.parse_output`, `parse_output_mixture`). A physical sanity gate rejects H2 > 71 g/L and SF6 > 1,880 g/L (`config.py:620, 688`).
- Where it runs and how results return: the authors' PBS/Torque cluster over SSH (`config.py:767-777`: `HPC_HOST="hpc"`, `HPC_BASE_DIR="~/llm2por"`, node property `ac`, poll every 300 s, give up after 24 h, at most 3 SSH retries only on rc=255). Two-stage HPC pipeline (`run_live_experiment.py:768-1064`): **R1** = 100 Z + 30 A + 30 F + 30 total `stage1_only` jobs (PORMAKE+LAMMPS+Zeo++) submitted by `hpc/submit_iteration.sh` (one qsub per MOF, ppn=1, walltime 4 h, queue `long`, batches of 48) or `submit_iteration_packed.sh` (4 per qsub); poll `.DONE` files (`_hpc_poll`, l. 590-723; resubmission disabled 2026-09-04 after cluster-admin request); `aggregate_results.py` -> `batch_results.json`; local Z filter (strict Zeo++ gate, top 10, fallback by `compute_geometry_match_score`, metal-stratified), A/F/total top 10 stage-1 successes; **R2** = `stage2_only` RASPA jobs; `collect_results.py` -> `LiveResults` -> `feedback_live_adapter.live_results_to_filter_sets` -> the same `FeedbackGenerator`. Everything crosses the wire as JSON: `batch_manifest.json` up, `batch_results.json` down (§3.2). Local-mode equivalent exists (`live_runner.run_live_iteration`) and a `--prepare/--collect` manual mode with `checkpoint.json` / `handoff_state.json` (`hpc/run_prepare_step.py`, `run_collect_step.py`).

### 2.11 The feedback generator — exactly what goes back to Agent 1
Text assembled by `FeedbackGenerator.generate_feedback` (`feedback_generator.py:640-666, 715-751`), in order:

1. `render_facts_only()` ledger block (if enabled) — best-so-far value + structure + iteration; top-K cutoff and median; top-5 list; geometry ranges of the frontier; cutoff trajectory.
2. `*** EXPERIMENT: 4-BEAM DIAGNOSTIC ***` then for each of Beam 1..4: a `to_string` table with columns `Structure | <metric name with unit> | Di (A) | Df (A) | SA (m2/cm3) | VF | Density (g/cm3) | Dif (A) | CV (A3)` (PORMAKE; hMOF drops Dif/CV; QMOF shows LCD/PLD/Density/Geometry/Ox. States; live adds a `GeoFilter` column PASS/fallback(reason)), sorted best-first, <=10 rows; a `--- Chemistry Profile (Beam k) ---` block with anonymous `MOF-i: Metals:[..] NodeFeatures:[..] LinkerFeatures:[..] Bkbn:[..] Subs:[..]`; a `--- Pattern Summary (Beam k) (N=n) ---` with top-3 metals/backbone/substituents/features as `name(pct%)`, "Minority (informational, do NOT require as mandatory)", and `Di/Df/SA/VF: min-max (med)`, capped at 500 chars; and a one-line interpretation hint per beam ("Compare with Beam 2 ...", "If Beam 2 >> Beam 3, your linker choice is adding value", "if Beam 2 >> Beam 4, your chemistry is better than random").
3. `=== GEOMETRY PROFILE OF YOUR CHEMISTRY (observational, not prescriptive) ===` — for PORMAKE mode only: min/max/median of vf, di, df, sa over the top-5 of Beam 1 (falls back to Beam 2/4) with "suggest target_x_min: 0.9 x lo" (l. 762-820); explicitly withheld when Beam 1 is empty.
4. `*** DIAGNOSTIC FOOTER (NO MATCHES FOUND) ***` only when Beam 1 is empty: which stage failed (chemistry / geometry / mismatch) using the matchmaker diagnostics (l. 569-638).
5. Live-only alternative payloads: `[MATCHMAKER FAILURE — No simulations ran this iteration]` listing available (metal, CN) node counts (`run_live_experiment.py:511-587`) and `[GEOMETRY ABORT — No simulations ran this iteration]` with target-vs-actual descriptor ranges (l. 726-765).

What is **never** sent: database identity and record ids, database size, global distribution, percentiles, thresholds, the sensitivity report (EF@1/5/10%, Mann-Whitney p — "Purpose: Human analysis ONLY - NOT shared with Agent 1", `sensitivity_analyzer.py:5, 32`). Note the Xe/Kr feedback includes the `Counts[...]` block referred to by the prompt only where `rule_based_counts` exist.

### 2.12 The two execution modes (Fig. S1; SI Note S1 `SI.txt:4` l. 81-95)
"The two operating modes are one implementation. Both mode drivers instantiate the same three agent classes, and the hypothesis-generating agent receives no signal indicating which mode it is running in." Differences: (a) evaluator — table look-up (`SensitivityAnalyzer` on the hidden CSV/index) vs live assembly+simulation (`live_runner` / HPC); (b) discovery "over-generates candidates to absorb assembly and simulation failures and reports the successfully simulated structures, whereas database mode reports a random sample of the matched candidates"; (c) random beam metal-balanced from the DB vs uniform over the generative space. Code-level extras: live shows `nlargest` (§2.6); live Beam 1 is MOF2Zeo pre-ranked (selection intensity asymmetry the paper acknowledges, `Manuscript.txt:14` l. 458-462); live iteration counting excludes failed iterations; live has `SimCache` (append-only `sim_cache.jsonl` keyed by (topology,node,edge), `live_runner.py:377-414`) so repeats are free; DB mode's `beam_data.csv` records the full matched sets.

### 2.13 Metrics
- **Per-iteration beam median** of the full matched/simulated set, mean +/- SEM over 5 replicates (Fig. 2, 4, 5 captions); reference lines = database median, top-10%, top-1% (direction-aware; for minimisation the 10th/1st percentiles) (`SI.txt:44`).
- **Final-iteration DB percentile** of the Beam-1 median (Table 1, S7) and "iterations to top-10%".
- **Hit rate / enrichment** (Table S2): fraction of candidates *returned to Agent 1* (<=10 per beam per iteration, pooled over 5 replicates x 10 iterations; baseline always 500, Beam 1 155-473 because constraints can admit fewer than 10) that exceed the DB top-1% threshold; enrichment = ratio.
- **Top-tier definitions**: top-1% / top-10% = value thresholds on the full hidden table; representative best = highest on-mechanism structure with its global percentile rank (Table S1).
- Human-only sensitivity report per iteration (`Sensitivity_Report_iterN.csv`): count, % removed, EF@1/5/10% via `Original_Rank`, Mann-Whitney U (one-sided) vs total, top-5/worst-5 means; unreliable flags below N=30; theoretical design space N x L x T (`sensitivity_analyzer.py:256-368, 370-482`).
- Discovery: Mann-Whitney one-sided on pooled structures, sign test at replicate level, violins trimmed to 0.5-99.5 pct (`SI.txt:32`).

### 2.14 Baselines and the budget-matching protocol (Notes S6, S7, S14)
- **GA** (`SI.txt:12`): same single-node/single-edge space and matchmaker vocabulary; 5 replicates x 10 iterations; 40 random valid MOFs simulated at iteration 1 form the surrogate training set; surrogate on categorical (topology, node, linker) retrained each iteration; GA within each eligible topology over node-linker pairs, population 200, 20 generations, mutation 0.2; top 80 surrogate-ranked submitted to the same backend, up to 40 completed added to the history; held-out surrogate R2 ~ 0, MAE 6.2-6.8 g/L.
- **BO** (`SI.txt:13-14`): latent-variable GP (Comlek et al.) with 2-d latent per categorical -> 6-d, ARD-RBF, constant mean, EI acquisition; 40 random initial; per iteration up to 100 node-linker pairs per topology sampled, top 3 EI per topology pooled, top 80 submitted, up to 40 kept; fixed enumeration of 47,740 candidates (`SI.txt:34`).
- **Random**: Beam 4 structures.
- **Label accounting** (`SI.txt:34`): realised evaluations GA 327-368, BO 212-265, LLM4MOF <=400 (380 +/- 2 realised); EGMOF conditioned on 37.77 g/L, 5 retrains on 360 labels (n = 200 = 40 x 5), one on 1,000 (n = 40 of 78), released 18,463 model (n = 924 of 944); "label-free, property-agnostic pretraining is excluded for every method, including this work's geometry surrogate" (629,335 records). Figure 7a halves use different GCMC codes and "are never compared numerically".

### 2.15 Backend benchmark (Note S13) and cost (Note S8)
- Benchmark: six backends, seven tasks x five replicates, Agent 2 pinned (env `AGENT2_PROVIDER/AGENT2_MODEL/AGENT2_OPENAI_KEY`, `config.py:53-72`), first attempt only; "Constraint strictness, the share of iterations whose translated constraints match no candidate, varies from 2.3% to 34.9%"; per-task ANOVA "not stable between the two campaigns" (`SI.txt:33`; `source_data/noteS13_backend_variance.csv`: between-arm SD 3.9-13.3 vs within-arm SD 8.3-14.8 percentile points).
- Cost (`SI.txt:15`): GPT-5.2 at $1.75/M input, $0.175/M cached, $14/M output; per 10-iteration discovery campaign 380 +/- 2 RASPA runs, 0.57 M tokens, **$1.06 +/- 0.05**; output tokens ~4% of volume but dominate cost; caching halves input cost; per-iteration cost rises from ~$0.03 to $0.19. `source_data/figure6_token_usage_and_cost.csv`: exactly **2 model calls per iteration** (Agent 1 + Agent 2), mean per iteration 39,958 non-cached + 12,687 cached input, 2,148 output tokens; per replicate $0.877-1.140; GCMC dispatched 36.5/iteration. Simulation compute cost is "accounted for separately via simulation count and are not included in the monetary figures"; no wall-clock is reported.

### 3.2 Stable interfaces (what a port must keep byte-compatible if it wants to reuse the loop)

1. **Agent-1 hypothesis JSON** — §2.2 schema; 7 prose fields + `meta_cognition.reasoning`; consumed verbatim as Agent 2's user message.
2. **Agent-2 constraint JSON** — §2.3 schema; consumed by all matchmakers, the analyzer (`geometry_filter`, `node_query.connectivity`), live beam construction (`_build_beam_specs` pops `geometry_filter` / linker fields / `global_requirements`), and the manifest (`config.geometry_filter`).

4. **Beam / candidate record** — a pandas row `filename, target, di, df, sa, vf, density, dif, cv` (+ mode-specific chemistry columns: `metals, topology, functional_groups(_categorized), readable_name, geometry, oxidation_states`; live adds `loading_*`, `component_*`, `match_score, geo_filter_passed, geo_filter_fail_reason`); `filter_sets = {"z","a","f","total", (+"d","e","e2","g",... empty in live), "_diag_info"}` (`feedback_live_adapter.py:187-245`); persisted as `beam_data.csv` with `beam_id ∈ {Z,A,F,R}` (`run_experiment.py:571-586`).
5. **Feedback payload** — the plain-text block of §2.11 (ledger + 4 beams + geometry profile + footer), or the two live failure texts; saved as `feedback_selected.txt`; ledger snapshot `memory_ledger.json` (`{mode, metric{name,direction,type}, global_best, frontier[], geometry_envelope{}, history[]}`).
6. **Ledger record** — frontier entry `{value, iter, beam, hypothesis_id, structure, filename, geometry{di,df,sa,vf,density}}`; history entry as in §2.8.

## 4. Domain-agnostic vs MOF-specific

**Domain-agnostic (port the design as is)**
- The five-stage loop with a fixed iteration budget, two-agent split (stateful hypothesiser / stateless translator), strict-JSON handoffs, halt on malformed JSON, per-iteration artefact layout (`agent1_output.json`, `agent2_output.json`, `beam_data.csv`, `feedback_selected.txt`, ledger, usage log). (§2.1-2.3)
- The beam idea: evaluate the full hypothesis and systematic relaxations of it (drop the numeric gate; drop the secondary chemistry; keep only the primary identity axis; unconditioned random) and report all four to the agent; attribution by comparing adjacent beams; identical sampling rule for every beam. What the three axes *are* is domain-specific (§4 below), but "full / minus gate / primary-only / random" is generic. (§2.6)
- Target-blind feedback: anonymised labels, no ids, no global statistics, no thresholds; identity-only stratified sampling that never reads the target; random beam excluded from memory. (§2.7, 2.11)
- The bounded facts-only ledger (best, top-K frontier, cutoff/median, envelope of the winners, cutoff trajectory) and the finding that prescriptive ledger text hurt. (§2.8)
- The evaluation protocol: hidden-table percentiles of the beam median, top-10%/top-1% thresholds, hit-rate/enrichment vs the random beam, 5 seeded replicates, first-attempt backend benchmark, budget-matched GA/BO/random arms, ablation of one component at a time, label accounting that excludes property-agnostic pretraining. (§2.13-2.15) Plus the aide2 additions: `--no-feedback` zero-feedback floor and `(NF-50)/(V0-50)` memorisation share, AUC-over-iterations metric, seeded battery driver.
- The two-level metadata philosophy: deterministic Layer-1 facts + deterministic SMARTS tags drive filtering; LLM-written names/hints are display-only. (§2.4)
- The surrogate-triage pattern (cheap predictor pre-ranks only the full-hypothesis beam; the oracle recomputes everything that is gated). (§2.9)
- The HPC job-array contract (manifest -> per-job JSON + DONE -> aggregate -> adapter) and the cache of already-evaluated candidates. (§2.10, §3.2)

**MOF-specific (must be replaced)**
- The candidate representation: (topology, node, edge) triples, the PORMAKE library (518/156/952), single-node/single-edge assembly, `topo+N+E` filenames, CIF serialisation, BB dictionaries and topology dictionary.
- The three attribution axes: geometry window (Zeo++ descriptors di/df/sa/vf/density/dif/cv), metal-linker chemistry, metal identity. In the Agent-1 toolbox these are also hard-wired as "pore geometry / functional-group decoration / electronic structure".
- The controlled vocabulary (124 MOF tags, coordination-tag handover, ditopic-only linkers, connectivity, nuclearity, open metal sites, oxidation state, coordination geometry) and the `{DATABASE_MODE_RULES}` blocks.
- MOF2Zeo and the geometry gate/fallback machinery; `GEOM_MARGIN_MODE`.
- The oracle: PORMAKE/LAMMPS-UFF/Zeo++/RASPA3, force fields, adsorbate registry, unit conversions (mol/kg <-> cm3STP/cm3 <-> g/L), sanity gates (71 g/L), PACMAN charges, `sim_safe_topologies`.
- The three hidden tables and their construction pipelines (MOFid decomposition, XYZ parsing, PORMAKE aromatic-bond SMARTS fix), `DATABASE_CONDITIONS.md`, `build_canonical_db.py`.
- Metric routing by keyword ("5 bar", "gravimetric", "band gap") and the QMOF band-gap categories in `config.BANDGAP_CATEGORIES`.
- Every English sentence in the feedback and in the prompts that names Di/Df/SA/metals/linkers.

Concrete polymer mapping the engineer will face (from the data audit, not from LLM4MOF): the candidate is a (monomer A, monomer B, composition, basis, architecture) tuple or a homopolymer repeat unit; the "hidden table" is the audited PoLyInfo Tg/Tm/density tables with the swap-safe binding (audit D1), dedup (D4) and trimer-key identity (D10); the natural analogue of the beams is full hypothesis (monomer chemistry + composition/architecture window + predicted-property window) / chemistry only (monomer family tags, no composition gate) / backbone-only (one axis, e.g. main-chain class, everything else free) / random; the "geometry gate" becomes a numeric gate on tabulated or surrogate-predicted descriptors (e.g. composition window, predicted Tg, MW); metal stratification becomes stratification by backbone class or monomer family so rare chemistries are shown; the vocabulary is a polymer SMARTS/tag set built with the same `5_shared/smarts_library.py` machinery; MOF2Zeo becomes a Tg surrogate (audit F1/F2) and the RASPA oracle becomes either the hidden table (DB mode, no simulation, the only mode that is cheap) or an MD/QSPR evaluator.

## 5. Known weaknesses and reviewer pressure points

Sources: aide2 roundtable (`2026-07-16_aide2-llm4mof_roundtable.md`), precheck design (`2026-07-17_...precheck-design.md`), `EXPLAINER.md`, `README.md`, `artifacts/results/{2026-07-17_w1_analysis.md, 2026-07-17_obvious-filter_probe-interpretation.md, 2026-07-18_w2_verdict.md}`, `ResponseToEditor.txt`, and my own reading.

1. **"Interpretability" is asserted, not measured.** The paper's evidence is three narrated trajectories (Fig. 3) and beam separation plots. There is no metric of explanation quality, no human evaluation, no test that the stated mechanism is causally responsible (e.g. by editing the hypothesis text and checking the beams move as predicted). The word "interpretable" in the abstract rests on the JSON being readable. The feedback hints literally tell the agent how to interpret the beams ("If Beam 2 >> Beam 3, your linker choice is adding value"), so the "reasoning" partially echoes the harness.

2. **Causal attribution via beams is not validated against a supervised baseline.** The aide2 obvious-filter probe (`obvious-filter_probe-interpretation.md`) fit a gradient-boosting model on the same hidden tables: PORMAKE H2-vol 100 bar OOF R2 = **0.943** from vf/sa/density alone ("geometry table is the answer key"); hMOF Xe/Kr Spearman 0.83 with pld argmax 4.9 Å (textbook); hMOF CO2 R2 0.73 with OMS importance 0.027 (the hMOF labels give **no reward for open metal sites**: OMS median 4.49 < non-OMS 5.14, also after VF control) — so the celebrated CO2 "open-metal-site prior overturned by feedback" (`Manuscript.txt:10` l. 293-297) is a *recovery* of a property of the generic-force-field oracle, not a chemical discovery. The paper never states oracle scope for the design rules; the C2H6/C2H4 section is the one place it does ("The force field used here does not represent the pi-complexation", `Manuscript.txt:18` l. 532-534).

3. **Memorisation share is substantial and unreported.** aide2 W1 (`w1_analysis.md`, n = 10/arm, GPT-5.2): with feedback replaced by an empty stub (`--no-feedback`), final Beam-1 percentile still reached 69.5 (T1 H2-vol) / 64.3 (Xe/Kr) / 78.4 (band-gap) vs 94.8 / 82.2 / 89.5 with feedback; floor-corrected memory share (NF-50)/(V0-50) = **0.44 / 0.44 / 0.72**. The band-gap task is "dominated by parametric memory" (GPT already knows Cu/Co/Mn -> low gap). The paper's "blind to database landscapes" refers to the loop, not to the pretraining corpus, and no zero-feedback control appears in the manuscript.

4. **Run-to-run stochasticity dwarfs strategy effects.** W1: σ of the final Beam-1 percentile = 6.4 (T1), 15.9 (T2), 6.9 (T3); AUC σ 3.3 / 8.2 / 3.2. W2 (`w2_verdict.md`, 210 campaigns, 14 variants x 3 tasks x 2 budgets, seeded): no variant beat the production configuration at Holm-corrected significance (max +1.80 σ), no budget-conditional rank reversal survived, and common-random-number pairing did not reduce variance because "LLM non-determinism dominates the campaign trajectory" even at temperature 0. Consequence for the paper: 5 replicates give SEM bars of several percentile points; Table 1's "within 0.1 points" is well inside noise (Note S13 admits per-task ANOVA is unstable); Table S1's Xe/Kr endpoint is 25.3 +/- 12.0.

5. **Metric exposure to constraint width.** The plotted beam median is the median of the *entire matched set*, whose size swings from 1 to >10,000 across iterations/arms (aide2 "B1-n diagnostic": T1-L V0 had median Beam-1 n = 1). A hypothesis that admits one structure yields a "median" of one structure; Table S2's hit rates are on the <=10 shown per iteration but the trajectories are on the full set. The paper does not report n per point (source_data does, `figure3_beam_descriptor_medians.csv` has counts).

6. **Leakage between DB mode and the matching DB.** The hidden table is the same object the matchmaker filters (`SensitivityAnalyzer.df_master` = the markscheme CSV; the hMOF/QMOF matchmakers filter the very index whose property column is the target). The agent never sees the values, but (a) the random beam is drawn from the full table with metal balancing, (b) the ledger's "outside promising" detector and the diagnostic footer are computed on the full sets, (c) in PORMAKE mode the readable names shown to the agent are unique enough to identify BB ids, and (d) the `readable_name` field used by the negative-tag bouncer is LLM-written. More importantly, the PORMAKE H2 tables were **pre-filtered to what the matchmaker can propose** (`build_canonical_db.py`) so "top-1% of the database" is top-1% of the reachable set; the paper's Table S1 n (14,173 / 9,533) are these filtered counts, `DATABASE_CONDITIONS.md` gives 19,997 / 12,188 valid rows before filtering.

7. **Budget fairness.** Nominal 40 x 10 for all arms, but realised GA 327-368 and BO 212-265 vs LLM4MOF 380 (Note S14) — GA/BO were handicapped by assembly failures and the paper counts that against them. LLM4MOF additionally spends ~190 relax+Zeo++ evaluations per iteration (100 Z + 3 x 30) that are "free" in the label accounting, plus a 629,335-record surrogate; the aide2 simulation persona priced this at ~25-35% of compute (roundtable S2). GA's surrogate had R2 ~ 0, i.e. it was random search with extra steps; BO used a 6-d LVGP with EI — neither is a strong baseline for a 12.5 M categorical space with 400 labels, which the authors concede (`SI.txt:14` l. 404-410). The EGMOF comparison uses a different GCMC code and is explicitly not a comparison.

8. **Live vs DB asymmetries the paper only partly discloses.** Beam 1 is MOF2Zeo pre-ranked from 100 while other beams are random 30 (acknowledged); Beam 1 candidates that fail the strict Zeo++ gate are still simulated as "fallback" to fill the quota (`live_runner.py:1155-1174`) and shown with a `GeoFilter` column — so "Beam 1 = full hypothesis" in discovery mode may contain structures that violate the hypothesis; live feedback shows the *best* 10 successes rather than a random sample; Beam 3 keeps the geometry filter in `_build_beam_specs`.

9. **Reproducibility of the released code.** NEW HEAD cannot import its own matchmaker or live runner (§0); env toggles are misnamed; the Claude provider used for three Table-1 arms is not in `llm_client.py`; MOF2Zeo training data not shipped; experiment logs (~1.6 GB) "upon reasonable request"; the DB-mode prompt build and the discovery/benchmark build differ and both are shipped, but `config.AGENT1_PROMPT_PATH` points to the discovery build.

10. **Scope limits the authors state** (`Manuscript.txt:22` l. 629-631): two-connected linkers only, single objective, single-node/single-edge frameworks, three discovery objectives, no experimental validation, generic force fields, charges only for CO2.

11. **Statistical framing.** "Enrichment 162x" on CH4 is a ratio with a baseline count of 1; Table S2 quotes two significant figures for such ratios. The one-sided sign test on 5/5 replicates (p = 0.031) is the minimum possible p-value at n = 5.

12. **Prompt-harness coupling.** Much of the "reasoning" is prescribed: the prompt dictates the axis menu, the exploration trigger (add >=3 metals, >=2 branches), the soft-count rule, the first-iteration no-numbers rule, and the read-the-evidence procedure; several are tuned empirically ("STAG fix reduces Z=0 from 7.3% to 0.9%", `config.py:148`). A reviewer can reasonably ask how much of the per-task "design rule" is the prompt's own decision procedure.

For LLM4POL this list is a checklist of what the polymer version must build in from day one: zero-feedback and supervised-shortcut baselines pre-registered; n per beam reported; oracle scope stated; replicate variance measured before claiming any effect; hidden table and candidate space documented as one object; budget accounting including surrogate/relax costs; interpretability measured by an explicit test (e.g. counterfactual edits of the hypothesis text, held-out rule transfer), not narrated.
