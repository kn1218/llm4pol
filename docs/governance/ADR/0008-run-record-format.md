# ADR-0008: The run record — what the ledger carries and how results are reduced from it

- **Status:** Accepted
- **Date:** 2026-09-29
- **Deciders:** agent, under the delegation the owner gave on 2026-09-29 ("직접 검토하고 결정해서
  운전"); each item is open to revision by the owner before the format freezes at the exit of M3
- **Relates to:** charter §7 and §13 M3, ADR-0003, ADR-0006, ADR-0007, DECISIONS-LOG D-21, D-26,
  D-31..D-38, `.planning/phases/04-run-management/04-RESEARCH.md`

## Context

The charter freezes the run record at the exit of M3 and requires that `replay` regenerate
`results.csv` from the ledger alone, byte-identical. The Phase 4 research measured four things the
one-line description of `results.csv` in the charter leaves open:

- A percentile needs the distribution it is taken in, and that distribution lives in a parquet the
  ledger does not contain.
- `feasible_frac`, `hits_top10` and `hits_top1` are column names with no definition in the charter or
  in LLM4MOF.
- D-26 quoted 42,733 for the population. That is a **row** count. The loop searches candidates:
  **39,454** pass the `check_tc` filter, against 40,212 for the README triple (measured 2026-09-29).
  The filter matters at the top of the distribution: it lowers the largest thermal conductivity from
  1.44 to 0.91 W/(m·K) and the top-1 % threshold from 0.513 to 0.450.
- A resumed run that starts with a fresh cache and budget meter diverges from the uninterrupted run
  at 6 of 13 crash points; one that rebuilds both from the ledger is byte-identical at 13 of 13.

LLM4MOF (`LLM2POR_Core`) separates two layers per beam: statistics over the full matched set, kept
for the log, and the sample the agent sees. Only the sample is paid for.

## Decision

1. **The ledger is the only state.** On `resume` the cache and the budget meter are rebuilt from the
   recorded `evaluation` events; nothing is carried in memory across a restart.
2. **The population travels in the ledger.** The `run_opened` event carries, for each named
   population, the objective value and each constraint value of every member as parallel arrays
   sorted by objective, without candidate identifiers. About 1 MB per ledger, which is untracked.
   Any metric over the population — including one redefined at the D-16 gate — is computable from the
   ledger alone.
3. **Two populations, one primary.** `check_tc` (39,454 candidates) is what the loop searches;
   `readme_triple` (40,212) is printed beside it. Membership follows the filter; values are the
   medians the evaluator serves, so a candidate is ranked among values the loop can observe.
4. **`results.csv` is long and reports the paid layer.** One row per iteration, beam and population:

   `iteration, beam, population, n_selected, n_ok, median_objective, feasible_frac, n_population,
   pct_of_population, hits_top10, hits_top1`

   | Column | Definition |
   |---|---|
   | `n_selected` | candidates in the recorded selection of that beam |
   | `n_ok` | selected candidates whose objective status is `ok` |
   | `median_objective` | median of the `ok` objective values; empty when `n_ok` is 0 |
   | `feasible_frac` | selected candidates whose constraint values are all `ok` and satisfy every constraint, divided by `n_selected`; a missing constraint value is not feasible |
   | `n_population` | members of the population with a non-null objective |
   | `pct_of_population` | share of the objective values of the population strictly worse than `median_objective`, times 100; "worse" follows `objective.direction` |
   | `hits_top10`, `hits_top1` | selected candidates that are feasible and whose objective is at least as good as the value of the ⌈0.10·m⌉-th / ⌈0.01·m⌉-th best member, where m counts the **feasible** members of the population |

   Thresholds, direction and the constraint list are read from the problem spec in the ledger header;
   none is a literal in the reducer. The matched-set (audit) layer is defined with the beams in M4 and
   gets its own file then; it is never mixed into these columns.
5. **Evaluation events are per candidate.** A crash inside a beam loses at most one candidate.
6. **`run_summary.json` is a fifth file**, written at `run_closed` and regenerated by `replay`:
   completed iterations, per-beam percentile and count trends with their iteration numbers, and the
   sha256 of `ledger.jsonl` and of `results.csv` (ADR-0007).
7. **`resume` refuses** a ledger whose header names a different snapshot, registry version or
   `code_git_sha` than the running code, and a ledger with a torn final line; it reports the offset
   and repairs nothing. `replay` and `usage` do not compare the code version.
8. **The selector is a protocol owned by `llm4pol.run`.** Phase 4 ships one complete implementation,
   a selector that replays a plan read from a file; Phase 5 adds the deterministic selector in
   `llm4pol.loop`, which imports the protocol. `llm4pol.run` never imports `llm4pol.loop`.

## Alternatives considered

| Option | Why not |
|---|---|
| Record the rank of each candidate at run time instead of the population | Compact, but a metric redefined at the D-16 gate could not be recomputed from the ledger |
| Record computed metrics and let `replay` tabulate them | `replay` would format rather than re-derive; an error in the metric would be replayed faithfully |
| Hits counted over all members, feasible or not | Under a constrained objective a candidate that violates a constraint is not a hit, however high its objective |
| Serve medians over `check_tc`-passing rows only | The cleaner semantics, but it changes values frozen at M2; two of 39,454 members are affected. Recorded as an option to revisit at the D-16 gate |
| Wide `results.csv` with one column set per population | Column count doubles with every population added |
| `resume` with a flag that accepts a code change | A run continued under different code is two runs in one record |

## Consequences

- Charter §7 run-record block and REQUIREMENTS `LOOP-06` are updated to these names in the change
  that adopts this ADR (charter v1.1).
- The figure in D-26 is corrected from 42,733 (rows) to 39,454 (candidates); the filter it chose is
  unchanged.
- **Guards**, all in M3: a test that a resumed ledger and its `results.csv` equal the bytes of the
  uninterrupted run at every event boundary; a test that reduces a committed fixture ledger and
  compares the sha256 with a constant on both CI platforms; the schema
  `protocol/schemas/ledger-event.json` in the `schema-inventory` step; an import-linter contract for
  `llm4pol.run`.
